# Colvenna Catalog 1.0 设计

本文是 Colvenna Catalog 1.0 的设计，供拆解实施计划使用。对外承诺见 [新闻稿](../product/press-release.md)，竞品、引擎与无服务器约束的事实见 [竞品调研](../research/paimon-catalog-landscape.md)（取数 2026-10-23）。服务端的现有实现见 [colvenna-catalog LLD](colvenna-catalog-lld.md)，它随代码从 colvenna-lake 导入。

文中标"需求方决定"的是需求方在 2026-10-23、24 的讨论中定下的；标"设计方决定"的是写设计时做的选择，需求方可以推翻；其余留给实施方。

## 1. 意图

把 colvenna-catalog 之于 Paimon，做成 Polaris 之于 Iceberg：一个独立、开源、不绑定厂商的 Paimon REST catalog 服务端，不装 colvenna-lake 也能用，colvenna-lake 只是它的一个使用方（需求方决定）。

**为什么。** 在 AWS 上用 Paimon 的团队正在"自研"和"选成熟方案"之间犹豫，又不愿把 catalog 托管到另一朵云上，那会增加复杂度和成本（需求方决定）。而 AWS 上没有能用的 Paimon REST catalog：Paimon 只有测试用的 mock 服务端，唯一的托管实现阿里云 DLF 闭源、只在阿里云上，Glue、S3 Tables、EMR、Athena 都不支持 Paimon，开源侧没有成熟实现（调研结论 1–3）。让这些团队放弃自研的，是两件事：自研要自己测兼容性，以及使用费用（需求方决定）。

**成功的样子。** 第一步，Paimon 用户选 catalog 时默认首选 Colvenna Catalog。第二步，Colvenna Catalog 同时管 Paimon 和 Iceberg，装了它就不必再装 Polaris（需求方决定）。

## 2. 目标、非目标与反目标

### 1.0 的目标

1. **兼容性不用用户自己测。** 一张公开的"引擎 × 版本"兼容矩阵，覆盖 Flink、Spark、Doris、StarRocks；每一格都对应一条测试，用户能在自己的账号里一键重跑（需求方决定）。
2. **费用算得清，空闲时没有常驻计算。**
   - 无服务器形态：没有请求时计算费用为 0。
   - EKS 形态：固定 2 个副本。
   - 元数据库（RDS/Aurora PostgreSQL）由用户自带，不计入；VPC 里的 NAT、接口端点等网络设施也算用户已有的基础设施（需求方决定）。
3. **装进用户自己的 AWS 账号，只依赖 AWS 自带的组件**（S3、STS、IAM、RDS/Aurora，以及所选形态的 EKS 或 Lambda/API Gateway）。在已有 EKS 集群与 PostgreSQL 的账号里，一条命令、15 分钟内装好并可读写（设计方决定，需求方已认可这个目标）。
4. **发布满足第 9 节的七项 Release 交付物与接收条件**（需求方决定）。

### 非目标（1.0 不做）

- 一个实例多个 catalog（warehouse）、Polaris 式的角色授权、AWS 以外的云（需求方决定）。
- Iceberg REST 接口。它是第二阶段，见第 10 节（需求方决定）。
- 为"空闲不花钱"更换或改造元数据库：不换 Aurora DSQL，不依赖 Aurora 自动暂停，存储层不动（需求方决定）。
- OIDC 等外部身份提供方。认证沿用服务端签发的不透明 bearer token（colvenna-lake 2026-10-13 的决定，不变）。
- 新的命令行工具。管理面用 REST API，1.0 提供它的 OpenAPI 描述与 `curl` 示例（设计方决定）。

### 反目标（做出来也算失败）

- 变成又一个要注册账号才能用的 SaaS，或者装起来需要的外部依赖比自研还多。
- 对外说"比托管 catalog 便宜"。只比服务费不成立（托管 catalog 每月 $0–$81，调研 1.4 节）。对外只说没有服务费、空闲时没有计算费用（需求方决定）。
- 任何匿名可达的 API 或资源；任何 Lambda Function URL（用户的安全红线）。
- 宣传材料里出现没验证过的能力。没验证的就不写，写了的就必须有测试。

## 3. 约束

- **许可与仓库。** 许可证是 Apache License 2.0。仓库迁到 colvenna 组织的 `colvenna/colvenna-catalog`，以一个 init 提交开始，先 private；兼容矩阵中声明支持的格子全部通过、费用实测完成后发 v1.0.0；本仓库与 Colvenna Lake 都判 GO 之后，两个仓库才转 public（需求方决定，2026-10-30）。
- **名字。** 产品名 Colvenna Catalog；技术标识与 Colvenna Lake 一致：`colvenna-catalog`、`COLVENNA_*` 环境变量、`/colvenna/admin/v1` 管理路径，本仓库自己的包名是 `com.colvenna.catalog`（#31，需求方决定）。命名沿革：导入时沿用改名前的 cove-catalog、`COVE_*`、`com.covelake` 与 `/cove/admin/v1`（需求方当时的决定），v1.0 发布前随 #31 全部改名。
- **不带 git 历史。** 新仓库从一个导入提交开始，提交信息注明来源 `cove-lake@<SHA>`（Colvenna Lake 改名之前的名字）。colvenna-lake 的历史里有部署环境的标识，后来才换成占位符；提交信息里的 issue 编号指向 colvenna-lake（需求方决定）。
- **colvenna-lake 的发布期间不动 colvenna-lake。** colvenna-lake 的 v1.0.0-rc.1 正在做发布验收（colvenna-lake #181、#204、#207）。在此期间：
  - 新仓库是 colvenna-catalog 的唯一开发处。
  - colvenna-lake 里只修阻断发布的问题，每个修复都移植到新仓库，并记下来源 SHA。
  - colvenna-lake 发布后，在 colvenna-lake 另开 issue，删掉其中的 `colvenna-catalog/`，改为按 digest 引用本仓库发布的镜像和 chart（需求方决定）。
  - 为了让 colvenna-lake 的已有环境能原地接管，导入时保留数据库迁移链（`V1`、`V2`……），不重置也不合并。通用 chart 与 CDK 应用里的资源名（命名空间、服务账号、Secret、角色名、标签）全部可以配置，colvenna-lake 切换时沿用自己现有的名字。原地接管在 colvenna-lake 的切换 issue 里验证，不在本仓库的 UAT 范围内（设计方决定）。
- **CI。** GitHub Actions 能跑就用；跑不了，就沿用 colvenna-lake 的做法：每个合并请求在确切的 SHA 上本地执行全部作业并留下记录，发布说明里记为豁免（需求方决定）。
- **安全底线。**
  - 所有 API 都要求认证，没有匿名路由。
  - 每个入口都要用未认证和越权的请求做负向测试。
  - 禁止 Lambda Function URL：CDK、CloudFormation、CLI 与第三方工具一律适用，评审时 grep `FunctionUrl` 与 `Lambda::Url`。
  - 文档、issue、回执里只写占位符（`<ACCOUNT_ID>`、`example.com`、`<ARN>`），不写账号 ID、ARN、真实域名与内网地址。
- **开发阶段不保证跨版本兼容。** 1.0 之前允许破坏性升级，不补跨版本回退演练（colvenna-lake 2026-10-14 的决定）。1.0 声明支持的升级与恢复路径仍要验证。
- **Paimon 版本。**
  - 1.0 的服务端仍依赖 Paimon 2.0.0，契约以 Paimon 2.0.0 发布的 REST OpenAPI 1.0 为准。
  - 兼容矩阵同时覆盖 Paimon 2.0.0 与 2.1.0（2026-10-12 发布）的客户端。
  - 上游契约测试用 2.0.0 的测试 jar；2.1.0 的测试 jar 如果能对同一个服务端运行，也加进来（设计方决定）。

## 5. 架构

服务端只有一份代码，以两种形态运行：

```text
引擎（Flink/Spark/Doris/StarRocks，Paimon RESTCatalog 客户端，token.provider=bear）
        │ HTTPS + Bearer
        ├── EKS 形态：Service（集群内）或内部 NLB ──► colvenna-catalog Pod × 2 ──┐
        └── 无服务器形态：私有 REST API（API Gateway）+ Lambda authorizer       │
                              └──► Lambda（colvenna-catalog + Lambda Web Adapter）─┤
                                                                               ▼
                                   用户的 PostgreSQL（RDS/Aurora）   用户的 S3 warehouse   STS（按表凭证）
```

- 两种形态共用同一个镜像、同一份 `COLVENNA_*` 配置契约和同一个数据库模式。两者的差别只能落在配置和入口上，不能分叉出两套业务代码。
- 元数据库、S3 桶与 VPC 由用户提供，或者由 CDK 应用新建最小的一套（第 6.3 节）。

## 6. 部署形态

### 6.1 EKS 形态

- 通用 Helm chart，发布为 OCI chart。
  - 去掉对 colvenna-lake 安装器、`colvenna-lake.io/*` 标签、从 EKS 节点组读取 `eligibleNodes` 的依赖。
  - 保留 2 个副本、尽量分布在不同节点、PDB `minAvailable: 1`，不加 HPA（需求方决定）。
- 入口默认是集群内的 Service，用 NetworkPolicy 只放行带指定标签的命名空间；需要从 VPC 内、集群外（例如 EMR）访问时，可以开一个内部 NLB。不提供面向公网的入口（设计方决定）。
- EKS 新集群的 VPC CNI 默认不执行 NetworkPolicy（colvenna-lake #164 的发现）。`install.sh` 的处理（设计方决定）：
  - 预检时检查集群是否执行 NetworkPolicy。不执行时默认拒绝安装，并说明怎样开启。
  - 用户可以显式加 `--allow-unenforced-network-policy` 继续安装。手册写明此时只靠认证保护，"绕过预期入口"的负向用例对这种配置记为不适用并写明理由。
  - `install.sh` 从不改动用户集群的 CNI 配置。UAT 用的集群开启执行。
- TLS 沿用现状：服务端自己终止 TLS，证书来自私有 CA。引擎的信任库是 JDK 自带的 `cacerts` 加上这个 CA。
- 身份：EKS 上的 Pod 身份（IRSA）。按表凭证沿用现在的签发方式：用服务账号 token 直接调 `AssumeRoleWithWebIdentity`，不经角色链，会话 1.5–12 小时。

### 6.2 无服务器形态

#### 入口（设计方决定）

- **API Gateway REST API，私有端点**：只能从用户的 VPC 经 `execute-api` 接口端点访问。
- **Lambda authorizer（REQUEST 类型）**：读取 `Authorization` 头，用与服务端相同的 token 校验，结果可以缓存；服务端收到请求后自己再认证一次。
- 选 REST API 而不选 HTTP API，是因为只有 REST API 支持私有端点。Paimon 客户端只会发 `Bearer` 或 DLF 签名，不会 SigV4，所以 IAM 授权不可用；token 是不透明字符串，不是 JWT，JWT authorizer 也不可用（调研 7.3 节第 7 条）。
- 不用 Lambda Function URL，不用 Lambda Web Functions。

#### 计算

- Lambda 运行同一个镜像，用 AWS Lambda Web Adapter 把调用转成本机 HTTP 请求。
- Lambda 是唯一空闲时计算与入口都不计费的方案（调研 7.3 节第 8 条）：Fargate 最小 0 个任务时 ALB 回 503，App Runner 已不对新客户开放。
- 执行环境内的回环连接可以不走 TLS，因为 TLS 在 API Gateway 终止。但 token 不能出现在回环之外的明文链路上。所以"Lambda 内允许回环明文"要做成一个只有 Lambda 形态才生效的显式配置，不能复用 `COLVENNA_ALLOW_PLAINTEXT`。

#### 必须解决的硬约束

来自调研 7.3 节，实施时先用 spike 验证：

1. **按表凭证不能经角色链。** Lambda 执行角色的凭证本身就是角色会话，再 AssumeRole 数据角色会被限制在 1 小时以内；而 Paimon 客户端在凭证剩余不足 1 小时时就会刷新，`COLVENNA_DATA_TOKEN_DURATION` 只允许 1.5–12 小时。
   - 要找一种不经角色链、也不新增任何匿名可达资源的签发方式。
   - 第一个要验证的候选：Cognito 身份池的开发者认证身份。Lambda 用自己的凭证调 `GetOpenIdTokenForDeveloperIdentity`，再用拿到的 token 调 `AssumeRoleWithWebIdentity`，带上按表的会话策略。这是推断，未核实。
   - spike 不通过时，1.0 的无服务器形态不支持按表凭证：`COLVENNA_DATA_TOKEN_MODE` 保持默认的 `disabled`，引擎用自己的 S3 角色访问表数据。手册与兼容矩阵写明这一点（需求方决定）。
2. **请求体上限。** Lambda 同步调用 6 MB、API Gateway 10 MB，服务端现在接受 64 MiB。无服务器形态的上限按入口设定，并写进手册；兼容矩阵要记录各引擎实际的请求大小。超限的请求必须得到明确的错误，不能部分生效。
3. **超时。** REST API 默认集成超时 29 秒，服务端主池的锁等待是 30 秒。无服务器形态要把锁等待与 S3 调用超时设到网关超时之内，让服务端在网关超时之前返回明确的错误。客户端重试已经提交过的请求时，仍然只能生效一次。
4. **冷启动。** Lambda 初始化（或 SnapStart 恢复）限 10 秒。
   - 数据库迁移不在函数初始化里做，改由安装脚本以 `migrate` 命令执行。
   - 连接池按"一个执行环境同时只处理一个请求"来设大小。
   - 用预留并发限住数据库连接总数。
   - 冷启动耗时属于性能文档的范围（第 9.3 节）。
5. **包大小。** `paimon-s3`、`paimon-format`、`paimon-core` 三个 jar 已约 126 MB，用容器镜像打包。

第 2–5 条中任何一条做不到时，1.0 只发 EKS 形态，无服务器形态放到 1.1；新闻稿与宣传材料随之去掉无服务器的内容（需求方决定）。第 1 条做不到不影响无服务器形态随 1.0 发布，按上面的降级处理。

### 6.3 AWS CDK 应用

- 一个独立的 CDK 应用，两种形态各一个栈。cdk-nag 合成即门禁，照搬 colvenna-lake 的做法。
- **两种模式**：
  - 接入用户已有的 VPC、子网、EKS 集群（EKS 形态）、S3 桶与 PostgreSQL；
  - 或者新建最小的一套：VPC、私有子网、S3 桶、RDS PostgreSQL 16，安全组只放行 catalog。
- **服务端角色**只能读写 warehouse 前缀下的元数据。**数据角色**只信任 catalog 的身份，允许 12 小时的会话。沿用 `catalog-stack.ts` 的权限设计，去掉 colvenna-lake 引擎角色等测试专用的部分。
- 不创建任何 `AWS::Lambda::Url`。`AWS::Lambda::Url` 与无认证入口在合成阶段就拒绝。

### 6.4 安装脚本

根目录的 `install.sh` 是两种形态共同的安装入口，满足第 9 节对安装脚本的要求：

- 有帮助信息与参数校验；Region 由显式输入给出。
- 预检：工具与版本、身份、账号、Region、集群、数据库连通性。
- 只装固定的发行物：按发布清单的 digest 装镜像与 chart。
- 安装前显示目标账号、Region、集群和版本；拒绝不支持的 Region（中国区、GovCloud）、能力不足与资源错配。
- 重复执行幂等，中断后可以重跑恢复。
- 第一个管理员 token 直接写进 Secrets Manager 或 Kubernetes Secret，不打印。
- 卸载只删本环境的资源，默认保留数据库和 S3 数据。

## 7. 兼容矩阵

### 一格的定义

一格 = 引擎版本 × 引擎所用的 Paimon 客户端版本 × 部署形态。每格的结果按"表类型 × 操作"列出：

- **表类型**：主键表（带与不带 deletion vector）、append 表。
- **操作**：建库建表与删除、写入并提交、读、按表凭证、端点覆盖检查（引擎没有调用服务端未提供的端点）。

### 1.0 的最小集合（设计方决定，需求方定了引擎）

| 引擎 | 版本 | Paimon 客户端 | 接入方式 | 写 | 读 | 按表凭证 |
| --- | --- | --- | --- | --- | --- | --- |
| Flink | 1.20；2.2 | 1.20 用 2.0.0 与 2.1.0；2.2 用 2.1.0 | Paimon 官方连接器，`metastore=rest` | 是 | 是 | 是 |
| Spark | 3.5；4.1 | 3.5 用 2.0.0 与 2.1.0；4.1 用 2.1.0 | Paimon 官方连接器，`metastore=rest` | 是 | 是 | 是 |
| Doris | 4.1.5 官方镜像 | 自带 1.4.2 | `paimon.catalog.type=rest`，`paimon.rest.*` 透传 | 否 | 是；带 deletion vector 的主键表按实测结果写明 | 是 |
| StarRocks | 4.1.6 官方镜像 | 自带 1.3.1 | `paimon.catalog.type=rest`，`paimon.option.*` 透传 | 否 | 是 | 否：配一份只读 S3 凭证，在格子里写明（需求方决定） |

### 规则

- **声明支持与已知限制。** 执行前把每一格（细到表类型与操作）标为"声明支持"或"已知限制"，写进本候选的必需用例集合。
  - 声明支持的格子必须通过才能 GO。
  - 上游引擎自身不兼容造成的不通（例如引擎自带的 Paimon 客户端版本过旧、引擎没有实现某项能力），记为已知限制，如实写明现象与原因，不挡发布（需求方决定）。
  - 按这条规则：Doris 4.1.5 自带的 Paimon 1.4.2 读不了带 deletion vector 的主键表，记为已知限制，1.0 不交付 Doris 读取器；StarRocks 4.1.6 如果经参数透传根本连不上，1.0 不带 StarRocks 发布，记为已知限制，等 StarRocks 发布带 Paimon 2.0 的版本后再补（需求方认可）。
  - Colvenna Catalog 自身的缺陷不能记为已知限制。
- 每格的结论只来自实测。不能工作的组合也留在矩阵里，写明现象和原因，不从表里消失。宣传材料只引用通过的格子。
- **一键重跑。** 用户给出 catalog 地址、token 与一台能访问它的主机，一条命令跑完自己关心的格子，并生成和发布版同样格式的结果。
  - 引擎以容器运行，不依赖 EKS，这样无服务器形态的用户也能跑。
  - 运行只用合成数据，结束时删除自己建的库与表。
- 矩阵是 UAT 的一部分：每一格对应第 9 节的一条功能用例。用户可读的矩阵页面由 UAT 报告生成，与报告同属一个候选版本。

### 9.2 UAT

**范围。** 以 colvenna-lake 的 UAT-CAT-01 到 12 为起点，扩成本产品的用例：

- **功能**：兼容矩阵的每一格（第 7 节）；授权与审计；按表凭证的范围与续期；管理 API。
- **安全**：每个入口都有未认证、越权、绕过预期入口的拒绝证据；不存在 Lambda Function URL 或没有有效认证的公开资源；健康端点不对外。
- **部署运维**：两种形态的从零安装、重复执行、中断恢复、配置拒绝、升级与回滚、卸载保留；元数据库从快照恢复。
- **故障恢复**：多写入方并发提交与故障下的原子提交；副本或执行环境故障后提交历史保持一致。

**配置。** 每个必需用例都要在两个标准 AWS Region（沿用 colvenna-lake 已验证的 `us-west-2` 与 `us-east-2`），对 1.0 发布的每种部署形态分别执行；只适用于一种形态的用例单列理由。

**环境。** UAT 与兼容矩阵只在本仓库自己的测试环境里运行，不与 colvenna-lake 的 uat、uat2 或任何其他仓库的环境共享（需求方决定）。

- 两个 Region 各一套，由本仓库的测试专用 CDK 栈创建：EKS 集群、RDS PostgreSQL、S3 桶，以及无服务器形态的入口。
- 测试时建，测完拆，只在运行期间产生费用。卸载只删除本仓库测试环境的资源。
- 需求方授权在部署账号里创建与删除这些资源。

**报告的完整性。** 报告必须包含：

- 候选标识、完整源码 SHA、镜像 digest、chart、`install.sh` 与用例文档的版本、执行日期。
- 账号（以占位符表示）、Region、形态、元数据库规格与关键配置。
- 每个适用用例的 ID、实际结果与预期的对照、执行时间、可核查的原始证据。
- `PASS`、`FAIL`、`BLOCKED`、`NOT_RUN` 的完整统计。必需但未执行的用例不能消失，也不能改成"不适用"。
- 失败与阻塞关联缺陷 issue、影响、修复版本与复测；复测要覆盖受变更影响的用例。
- 引用历史证据（包括 colvenna-lake 里的执行）时，保留原执行身份，并说明它对当前候选仍然有效的依据。

**边界。** UAT 不含吞吐、QPS、p95/p99、容量、压测、冷启动耗时与成本效率，这些全部进入性能文档，不计入 UAT 的用例数、通过率或结论。功能场景里的时间戳可以核对事件顺序，但不能证明性能达标。

### 9.3 独立性能测试

- **场景**：
  - 多写入方并发提交的吞吐与延迟；
  - 元数据读请求（取表、列表）的延迟与可承受的请求率；
  - 按表凭证签发的延迟；
  - 无服务器形态的冷启动（空闲后的第一个请求）与 SnapStart 恢复；
  - 两种形态在同一负载下的对比。
- **口径**：每个场景的环境、方法、指标、目标都要在执行前固定。目标由实施方提出、需求方确认后写进发布清单；实测结果附原始数据与限制。
- **约束**：无服务器形态的冷启动必须落在 Paimon 客户端的超时之内，客户端超时的实际值由实施方核实。
- **结论**：性能文档给出本候选的验收结论。性能移出 UAT 不等于豁免性能验收。

### 9.4 发布结论

- 发布检查报告给出明确的 `GO` 或 `NO-GO`，并列出阻塞项、已知限制与后续 issue。
- 出现以下任何一种情况，结论必须是 `NO-GO`，不能标记为已通过：
  - 七项交付物有缺失，或版本不一致；
  - 任一必需 UAT 用例是 `FAIL`、`BLOCKED` 或 `NOT_RUN`；
  - 性能验收没有达到执行前固定的口径。
- 安全扫描（ASH、Trivy、cdk-nag、许可证）没有未处理的发现。
- CI 豁免单独记录，不能替代 UAT 或性能验收。
- v1.0.0 的 GO 同时意味着：仓库转 public、镜像与 chart 发到 GitHub Container Registry：镜像 `ghcr.io/colvenna/colvenna-catalog`，chart `ghcr.io/colvenna/charts/colvenna-catalog`（需求方 2026-10-30 决定：公共制品只发 GHCR，不向 ECR Public 发布）。

## 10. 第二阶段：统一 Iceberg（1.0 不做，但不能堵死）

目标是装了 Colvenna Catalog 就不必再装 Polaris（需求方决定）。最少要接下 Polaris 今天在 colvenna-lake 里的全部工作（需求方认可）：

- Iceberg 读端（例如 Spark 加 Iceberg 1.10、Trino）经 Iceberg REST 只读访问 Paimon 以 Iceberg 兼容元数据（`metadata.iceberg.storage`）发布的表；
- 认证、授权与按表只读凭证和 Paimon 共用一套；
- 由平台决定哪个快照对外可见。

Iceberg 引擎直接在 Colvenna Catalog 里建表、写表，放到以后。

对 1.0 的约束：

- 表类型模型保留可扩展性：`ICEBERG_TABLE` 现在只在 PostgreSQL 中登记元数据。
- 认证方式能被 Iceberg 客户端使用。Iceberg REST 客户端能否直接带静态 bearer token，第二阶段开工前核实。
- Iceberg 接口将来放在独立的路径前缀下，1.0 的路由不要占用它。

## 11. 交付顺序

每一步都按 issue 交付，走评审、CI（或本地全套）与按 SHA 合并的流程：

1. **导入**：服务端代码、单元测试与契约测试、LLD，加上本地全套 CI（构建、Error Prone、spotless、测试）。
2. **EKS 形态的部署物**：通用 chart、独立 CDK 应用（两种模式）、`install.sh`、发布清单工具。
3. **兼容矩阵**：可重跑的测试框架，以及 Flink、Spark、Doris、StarRocks 的格子；先在 EKS 形态上让声明支持的格子全部通过。
4. **无服务器形态**：先 spike 第 6.2 节的五条硬约束（按表凭证优先），按第 6.2 节的规则决定 1.0 是否带这个形态以及是否带按表凭证，再实现并把兼容矩阵扩到这个形态。
5. **文档**：用户手册、部署指南、管理 API 的 OpenAPI、费用估算与实测、英文 README；LLD 改为本仓库自足的说明，去掉指向 colvenna-lake 的链接（导入时它们固定在来源提交上）；补上 NOTICE。
6. **UAT 与性能**：用例集合与性能口径在执行前固定；生成 `v1.0.0-rc.N`，在两个 Region、两种形态上执行；修复并复测，直到 GO。
7. **v1.0.0**：打 tag，仓库转 public，发布公共镜像与 chart。
8. **colvenna-lake 切换**：colvenna-lake 发布完成后，在 colvenna-lake 里另开 issue 执行（第 3 节）。

第 3 步与第 4 步的 spike 可以并行，其余基本按顺序进行。
