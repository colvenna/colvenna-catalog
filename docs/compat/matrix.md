1. Doris is read-only in 1.0 (design section 7): it reads the tables a Flink or Spark cell wrote, and the matrix does not run its writes.
2. Doris 4.1.5 bundles Paimon 1.4.2, whose batch scans of a deletion-vector table skip level 0: it does not read the rows still in uncompacted level-0 files (reading them, deletion-vectors.merge-on-read, takes Paimon 2.0); fully compacted tables read correctly. Measured: the level-0 rows by runs 20261028T120119Z-c93a, 20261028T122104Z-9305 and 20261028T122711Z-4166, the compacted tables by run 20261028T100928Z-e326, whose dataset compacted everything; first declared as 'cannot read primary-key tables with deletion vectors' (design section 7).
3. Declared a limitation before the runs, together with the read; the runs show the catalog issued Doris the table's credentials and Doris reading its compacted rows with them.
4. StarRocks is read-only in 1.0 (design section 7): it reads the tables a Flink or Spark cell wrote, and the matrix does not run its writes.
5. StarRocks 4.1.6 reads with short-lived S3 credentials of its own (UAT-CMP-08), and its JNI reader, which takes the primary-key table's splits that need a merge, fails the first such read after its BE starts, and can fail it after the catalog gets new credentials ('Provider TemporaryAWSCredentialsProvider has no credentials'); later reads pass. The cause is upstream (StarRocks/starrocks#81984): StarRocks 4.1.6 bundles paimon-s3 1.3.1, which carries Hadoop 3.3.4, whose TemporaryAWSCredentialsProvider gives no credentials to the calls made while its first call is still loading them (HADOOP-18233, fixed in Hadoop 3.3.5), and the BE's scanners share one cached S3AFileSystem. Measured by runs 20261030T150955Z-b7ee and 20261030T151725Z-9b62 of v1.0.0-rc.2's UAT, and run 20261028T093913Z-e9a6, and reproduced locally: 15 of 15 first reads after a BE start failed, none of 10 with the fixed provider patched into the jar, none of 4 with one scanner at a time. An IAM user's long-lived key read every time (runs 20261028T120119Z-c93a, 20261028T122104Z-9305 and 20261028T122711Z-4166; 3 of 3 locally), but the release gives StarRocks no long-lived keys.
6. StarRocks does not use the catalog's per-table credentials (design section 7): it reads with read-only S3 credentials of its own, short-lived credentials of a role in the release's UAT (an IAM user's access key in the runs of 2026-10-28). With short-lived ones, its JNI reader's first read of a primary-key table fails, as the pk read limitation says.
7. StarRocks 4.1.6 bundles Paimon 1.3.1, whose batch scans of a deletion-vector table skip level 0: it does not read the rows still in uncompacted level-0 files (reading them, deletion-vectors.merge-on-read, takes Paimon 2.0); fully compacted tables read correctly. Declared by inference from Doris before the runs; measured: the level-0 rows by runs 20261028T120119Z-c93a, 20261028T122104Z-9305 and 20261028T122711Z-4166, the compacted tables by run 20261028T100928Z-e326.
